# GabonConnect V0.3.0
## Roadmap Produit & Technique — Community Intelligence

**Statut :** cadrage de version (spécification uniquement, aucun code applicatif modifié)
**Branche cible :** `feature/v0.3.0`
**Version précédente :** V0.2.1 (agrégation `/news`, `/events`, `/opportunities` recettée)
**Locales cibles :** français par défaut, anglais disponible

## 1. Vision

GabonConnect V0.3.0 fait passer la plateforme d'un hub d'information communautaire à une plateforme **intelligente et personnalisée** : chaque membre — diaspora ou étudiant sur un campus — reçoit au bon moment les actualités, démarches et opportunités qui le concernent réellement, peut interroger un assistant ancré sur les données internes, et peut faire entendre sa voix sur l'évolution du produit.

### Objectifs de version

- Notifier chaque utilisateur uniquement sur ce qui le concerne (ville, pays, statut, centres d'intérêt).
- Répondre aux questions administratives et académiques via un assistant IA fiable, sourcé et vérifiable.
- Construire un feed d'accueil personnalisé plutôt qu'une liste chronologique unique.
- Calculer et expliquer un score de pertinence entre un profil et une opportunité/bourse.
- Refondre le feedback communautaire en module structuré, votable et transparent.

### Principes non négociables (hérités de V0.2.0, renforcés en V0.3.0)

1. **Explicabilité** : toute recommandation, notification ou réponse IA doit indiquer sa source et sa raison ("pourquoi je vois ceci").
2. **Consentement et minimisation** : la personnalisation ne collecte que les attributs strictement nécessaires (ville, pays, statut), avec opt-out possible.
3. **RAG ancré, pas de génération libre** : l'assistant IA ne répond qu'à partir de contenus indexés (base interne + sources officielles), avec citation systématique ou refus de répondre.
4. **Mobile first & FR/EN parité stricte** (inchangé depuis V0.2.0).
5. **Progressivité** : chaque pilier est activable indépendamment par configuration/feature flag, avec rollback documenté.

## 2. Les 5 piliers V0.3.0

### Pilier 1 — Notifications (In-App & Email/Push)

Étend le `NotificationCenter` de V0.2.0 (in-app uniquement) vers des canaux Email et Push réels, avec files d'attente, templates versionnés et respect strict des préférences déjà modélisées dans `NotificationPreference`.

### Pilier 2 — Assistant IA GabonConnect (RAG)

Assistant conversationnel ancré (Retrieval-Augmented Generation) sur la base de données interne (articles, procédures, bourses, événements approuvés) et sur les sources officielles enregistrées dans `SourceRegistry`. Aucune réponse sans passage de citation/source.

### Pilier 3 — Personalization & Dashboard

Feed d'accueil sur-mesure basé sur `Profile.cityId` (→ `City.countryId`) et un nouvel attribut de statut (étudiant / professionnel / association). Remplace la page d'accueil générique par un flux pondéré et explicable.

### Pilier 4 — Profile Matching Engine

Calcul d'un score de pertinence profil ↔ opportunité/bourse à partir d'une taxonomie de compétences/critères, réutilisé par le Pilier 3 (feed) et par des notifications ciblées (Pilier 1).

### Pilier 5 — Module "La Voix de la Communauté"

Refonte du feedback (actuellement une table Supabase `feedbacks` hors Prisma, gérée par [lib/feedback-admin-actions.ts](../lib/feedback-admin-actions.ts)) en un module Prisma structuré : soumission catégorisée, vote communautaire, statut de traitement public et lien vers la roadmap produit.

## 3. Dépendances techniques transverses

| Besoin | Dépendance |
|---|---|
| Ciblage des notifications Email/Push | Provider transactionnel (ex. Resend/SES pour email, Web Push/FCM pour push), files d'attente (cron ou queue table), templates i18n versionnés |
| Assistant IA (RAG) | Vector store (pgvector sur Postgres existant, ou Prisma + extension `vector`), pipeline d'embeddings (job d'indexation incrémental sur `Article`, `AdministrativeProcedure`, `Scholarship`, `Event`, `Opportunity` approuvés), fournisseur d'embeddings/LLM externe, gestion de clé API serveur-only |
| Personalization & Dashboard | Nouveau champ de statut utilisateur (`Profile.memberStatus` ou modèle `UserPreferences`), agrégation par ville/pays déjà disponible via `City`/`Country` |
| Matching Engine | Taxonomie de compétences/centres d'intérêt (nouveau modèle `Skill` + tables de jointure), champ `type`/`level` déjà présent sur `Opportunity`/`Scholarship` |
| Voix de la Communauté | Migration de la table Supabase `feedbacks` vers un modèle Prisma `CommunityFeedback` + `CommunityFeedbackVote`, réutilisation de `ContentModerationStatus` |
| Toutes | `NotificationType` étendu, RLS/permissions Supabase mises à jour en parallèle des migrations Prisma, feature flags par pilier |

## 4. Découpage des Tasks 058 à 067+

### TASK 058 — Audit d'Architecture V0.3.0 & Fondations de Données

**Périmètre :** inventaire des modèles impactés (`Profile`, `Notification`, `SourceRegistry`), conception du modèle `UserPreferences` (ville, pays, statut, centres d'intérêt, canaux de notification), extension de `NotificationType`, feature flags par pilier.

**Prérequis :** V0.2.1 recettée, schéma Prisma actuel validé, cartographie RLS Supabase existante.

**I18n FR/EN :** libellés des statuts (étudiant/professionnel/association), catégories de préférences, messages d'aide à la configuration.

**Sécurité :** `UserPreferences` liée strictement à `userId` (ownership), RLS lecture/écriture propriétaire uniquement, aucune donnée sensible exposée aux autres utilisateurs.

**Validation :** migration Prisma reversible, `npx prisma validate` → `npx tsc --noEmit` → `npm run lint` → `npm run build`.

### TASK 059 — Notifications : Canaux Email & Push

**Périmètre :** intégration provider email transactionnel et Web Push, table de file d'attente (`NotificationDelivery`), retry/idempotence, respect de `NotificationPreference` existant.

**Prérequis :** Task 058, choix du provider, clés API en variables d'environnement serveur-only, templates HTML/text.

**I18n FR/EN :** templates email/push versionnés par locale, fallback FR, formatage dates/échéances localisé.

**Sécurité :** clés API jamais exposées côté client, désinscription en un clic (lien signé), anti-spam (fréquence max par utilisateur), logs sans PII en clair.

**Validation :** tests d'envoi en sandbox, tests de préférence (opt-out effectif), `npx prisma validate` → `npx tsc --noEmit` → `npm run lint` → `npm run build`.

### TASK 060 — Notifications Ciblées Bourses/Démarches/Actualités

**Périmètre :** déclencheurs métier reliant publication de contenu approuvé (Scholarship, AdministrativeProcedure, Article) aux préférences de ciblage (ville/pays/statut) issues de `UserPreferences`.

**Prérequis :** Task 058, Task 059, catalogue d'événements métier (publication, échéance proche).

**I18n FR/EN :** raisons de notification explicites ("vous recevez ceci car..."), textes traduits et cohérents avec Task 041 existant.

**Sécurité :** déduplication stricte, pas de fuite d'information sur un contenu non public dans un aperçu de notification.

**Validation :** tests de ciblage (bon utilisateur/bonne raison), tests de non-régression sur les notifications V0.2.0, chaîne complète verte.

### TASK 061 — Assistant IA GabonConnect : Pipeline d'Indexation & Vector Store

**Périmètre :** activation de l'extension vectorielle Postgres, job d'indexation incrémental (embeddings) des contenus approuvés (`Article`, `AdministrativeProcedure`, `Scholarship`, `Event`, `Opportunity`) et des sources officielles de `SourceRegistry`.

**Prérequis :** Task 058, fournisseur d'embeddings choisi, quota/coût validé, stratégie de ré-indexation lors d'une mise à jour/suppression de contenu.

**I18n FR/EN :** indexation par langue (FR/EN) avec métadonnée de locale, pas de mélange de langue dans une réponse.

**Sécurité :** indexation exclusivement des contenus `moderationStatus = APPROVED` et publics, purge des embeddings lors d'une dépublication, clé API serveur-only.

**Validation :** job idempotent testé, cohérence embeddings/contenu vérifiée, `npx prisma validate` → `npx tsc --noEmit` → `npm run lint` → `npm run build`.

### TASK 062 — Assistant IA GabonConnect : Interface Conversationnelle & Garde-fous RAG

**Périmètre :** interface de chat, récupération top-k des passages pertinents, génération de réponse avec citations obligatoires (lien vers l'article/procédure source), refus explicite si aucune source pertinente.

**Prérequis :** Task 061, politique de contenu (sujets autorisés), limites de longueur/coût par requête.

**I18n FR/EN :** réponses et messages de refus dans la langue de la question, citations affichées dans la locale d'origine du contenu.

**Sécurité :** rate limiting par utilisateur, filtrage des injections de prompt via le contenu indexé, aucune donnée personnelle d'un autre utilisateur injectée dans le contexte, journalisation des requêtes sans PII sensible.

**Validation :** tests de citation obligatoire, tests de refus hors périmètre, tests de charge légers, chaîne `PRISMA VALIDATE → TSC → LINT → BUILD` verte.

### TASK 063 — Personalization & Dashboard : Feed d'Accueil Sur-Mesure

**Périmètre :** nouvelle page d'accueil connectée (remplace le flux générique), pondération par ville/pays (`UserPreferences`), statut étudiant/pro, et sources déjà consultées ; widgets bourses/démarches/actualités proches de l'utilisateur.

**Prérequis :** Task 058 (UserPreferences), contenus déjà géolocalisables (`City`/`Country` sur Association/Profile), Task 060 pour cohérence avec les notifications.

**I18n FR/EN :** libellés des sections du feed, messages d'état vide ("aucun contenu pour votre profil"), formats de date/lieu localisés.

**Sécurité :** le feed ne doit jamais révéler de contenu non approuvé ou privé à un autre utilisateur ; calcul de pondération côté serveur uniquement.

**Validation :** tests de pertinence par profil type (étudiant Paris, pro Montréal, sans préférence), non-régression sur les pages `/news` `/events` `/opportunities`, chaîne complète verte.

### TASK 064 — Profile Matching Engine : Taxonomie & Modèle de Score

**Périmètre :** modèle `Skill`/`Interest` et tables de jointure profil↔compétence et opportunité↔compétence, algorithme de score explicable (ex. recouvrement pondéré ville/domaine/niveau), stockage du score ou calcul à la volée.

**Prérequis :** Task 058, consentement explicite de l'utilisateur pour l'utilisation de son profil dans le matching, taxonomie validée avec le produit.

**I18n FR/EN :** libellés de compétences/centres d'intérêt traduits avec identifiants stables (pas de traduction littérale qui casserait le matching), raisons de score traduites.

**Sécurité :** RLS/permissions pour que le score ne soit visible que par le profil concerné (et l'auteur de l'offre côté agrégé/anonymisé), pas d'enumeration de profils via le matching.

**Validation :** tests d'équité (pas de biais discriminatoire sur des critères sensibles), tests de cohérence de score, chaîne complète verte.

### TASK 065 — Profile Matching Engine : Intégration Feed & Notifications

**Périmètre :** exposition du score de pertinence dans les cartes Opportunity/Scholarship, alerte notification si un nouveau contenu dépasse un seuil de pertinence pour l'utilisateur.

**Prérequis :** Task 063, Task 064, Task 060 (canal de notification ciblée).

**I18n FR/EN :** affichage du score et de sa justification traduits, seuils configurables sans casser la parité FR/EN.

**Sécurité :** anti-spam sur les alertes de matching (fréquence plafonnée), pas de sur-sollicitation.

**Validation :** tests d'intégration bout-en-bout (contenu publié → score calculé → notification envoyée si seuil atteint), chaîne complète verte.

### TASK 066 — Module "La Voix de la Communauté" : Migration de Données & Modération

**Périmètre :** nouveau modèle Prisma `CommunityFeedback` (catégorie, statut, auteur, upvotes) et `CommunityFeedbackVote`, migration des données existantes de la table Supabase `feedbacks`, admin de modération remplaçant [lib/feedback-admin-actions.ts](../lib/feedback-admin-actions.ts).

**Prérequis :** Task 058, export/backup de la table Supabase existante, mapping de statuts (`FeedbackStatus` actuel → `ContentModerationStatus` + statut de traitement produit).

**I18n FR/EN :** catégories de feedback, statuts de traitement ("en cours", "planifié", "livré", "refusé") traduits.

**Sécurité :** un utilisateur ne vote qu'une fois par feedback (contrainte unique), modération avant affichage public, protection anti-spam sur la soumission.

**Validation :** migration testée avec rollback, tests unicité de vote, tests de modération, chaîne complète verte.

### TASK 067 — Module "La Voix de la Communauté" : Feed Public & Vote

**Périmètre :** page publique listant les feedbacks votables/filtrables par catégorie et statut, formulaire de soumission connecté au profil, lien visible vers la roadmap produit (ce document) pour les feedbacks planifiés.

**Prérequis :** Task 066.

**I18n FR/EN :** page complète traduite, tri et filtres localisés, message de remerciement après soumission.

**Sécurité :** rate limiting sur la soumission, validation Zod stricte des entrées, pas d'exposition d'email/PII de l'auteur sur la page publique.

**Validation :** tests de soumission, vote, filtre, permissions, chaîne complète verte.

### TASK 068 — Audit Transverse V0.3.0 : Performance, Coûts IA, Confidentialité & Observabilité

**Périmètre :** revue des coûts d'appel LLM/embeddings, limites de débit globales, monitoring des files de notification, audit RLS complet sur `UserPreferences`/`CommunityFeedback`/nouvelles tables de matching, vérification parité FR/EN sur l'ensemble des piliers.

**Prérequis :** Tasks 058 à 067 livrées en staging.

**I18n FR/EN :** audit final de parité des clés de traduction sur tous les nouveaux namespaces.

**Sécurité :** revue des secrets (clés provider email/push/LLM), revue RLS, revue des logs pour absence de PII, test de charge léger sur le RAG et les notifications.

**Validation :** `npx prisma validate` → `npx tsc --noEmit` → `npm run lint` → `npm run build`, rapport d'audit signé avant activation en production.

## 5. Gouvernance et Definition of Done

Une Task V0.3.0 est livrable lorsque :

- son schéma/migration est documenté, reversible, et accompagné des mises à jour RLS Supabase correspondantes ;
- ses Server Actions et APIs valident session, rôle, ownership, consentement et entrées ;
- toute recommandation, notification ou réponse IA est explicable (source ou raison affichée) ;
- les tests couvrent succès, erreur, vide, permissions et régression sur les piliers V0.2.0 existants ;
- FR et EN ont les mêmes clés et des textes relus ;
- la chaîne `PRISMA VALIDATE → TSC → LINT → BUILD` est verte ;
- les variables d'environnement et coûts (email/push/LLM/embeddings) sont documentés dans `.env.example` ;
- aucune clé, donnée personnelle ou sortie de debug n'est committée.

## 6. Stratégie de livraison

Les Tasks sont livrées dans l'ordre 058 → 068, chaque pilier restant activable indépendamment via feature flag pour permettre un rollout progressif : Notifications (058-060) → Assistant IA (061-062) → Personalization (063) → Matching (064-065) → Voix de la Communauté (066-067) → Audit final (068). Les migrations sont déployées d'abord en staging ; les fonctionnalités à coût variable (LLM, embeddings, email/push) sont activées avec un budget plafonné et surveillé avant l'ouverture en production.
